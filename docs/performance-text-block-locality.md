# Text 分散窗口读取 / Grouped window reads（2026-11-13）

优化对象是**显式启用的实验性 Windowed Text**，尤其是耗时排序后访问分散的记录。
默认完整 Text、sidecar 自动分流策略、网络格式和版本号均不改变。无需新增运行参数；
重新生成报告后，仍按[窗口模式指南](performance-text-window.md)进入 `?text=windowed`。

## 问题与实现

展示顺序并不等于原始资源顺序。一个 160 单元的排序窗口可能需要几十个 512 行
绘制块，而其中多个绘制块属于同一个 4,096 行 HTML 网络资源。此前按展示次序启动
四个逐块读取任务，小缓存淘汰了仍需使用的资源，导致同一窗口重复下载、SHA-256
校验和 UTF-8 解码。仅把绘制块按 ordinal 排序，仍无法避免并发资源超过字节预算
时的重复读取。

- 窗口现在按**原始 ordinal 的网络资源身份**分组，最多四组并行，每组只读取一次。
  不把稀疏原始行号、过滤后的排列或显示位置当作资源下标。
- `fgData.loadTextBlocks(ordinals, options)` 在请求前拒绝非法或跨资源的 ordinal，
  复制请求数组，保留返回次序与重复块身份；空组不加载资源，预取消仍返回 AbortError。
  逐块接口复用同一实现，旧的按行读取和 Full Text 继续可用。
- 完整扫描网络资源内的绘制块边界，随后仍解析每个所需绘制块的**全部行**，校验
  范围、真实 ID、原文、展示属性及源码配对；不是只校验最终挂载的那 160 行。
  同资源剩余绘制块不再依赖 LRU 命中，但没有缓存离屏 DOM。
- 每解析一个绘制块仍让出执行机会，读取、解析及发布前检查取消；失败保留旧窗口，
  可重试。挂载始终按完整展示排列进行，不按资源读取次序显示。

HTML LRU 仍为 **4 块 / 16 MiB 已校验 UTF-8 字节**。在途的四组字符串及解析暂存
可超过这个缓存预算；行数也不限制单行字节数，因此这不是 JS heap、进程或峰值
内存上限。完整模型、耗时排列和完整绘制块解析仍有主线程开销。

## 测量方法

基线运行时 `a3401632341c`。两种规模均复用同一已生成真实 sidecar，只替换 HTML
入口中的三个相关前端资产；两边其余运行时、参数和不可变数据资源相同，没有
重抓 trace、减少记录或裁掉源码来换取速度。此次输入均未提供 vmlinux/DWARF，
源码展开为零；不能将性能结果外推为源码丰富报告的结论。

Chromium **145.0.7632.6**，1440×900，通过真实 `fgview` HTTP 访问。每种输入三对
独立浏览器，顺序 before/after、after/before、before/after；无 CPU Profiler，测量
期间没有并行测试或打包。每步开始前等待视口后台绘制结束且连续两帧空闲，避免
把上一操作的未完成请求误计为本次读取。

`--scattered` 在首次降序排序后增加三个真实跳行：排序首行、排序第 161 行、返回
首行；核对目标确实挂载后才成功。它们代表访问排序后的首窗、邻近窗口及返回，
不声称操作系统冷缓存。随后还测稳定窗口的重复重建、筛选与 Clear，不把已有
160 行可以完全复用的热重建，当成需要下载散布 HTML 的场景。

就绪时间是成功 API 的完整 Promise 耗时；同步前缀和两次 rAF 反馈另外保留，不
相互替代。请求数、不同资源数及 `encodedBodySize` 仅统计本次 API 开始之后发起、
在 API 完成之前结束的 Text HTML 读取；字节数不含 HTTP 头。后续视口反馈不混入
这组 API 资源指标。Long Task observer 可能漏掉注册前已开始的当前任务，零值
不是无卡顿或帧率保证。

仍有 429.2ms 同步工作。即使不必重新下载任何 HTML，也不能据此宣称流畅或卡顿
